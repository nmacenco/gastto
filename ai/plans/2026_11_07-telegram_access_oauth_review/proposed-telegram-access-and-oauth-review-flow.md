# Proposed Telegram Access and Google OAuth Review Flow

> Status: exploratory proposal. No product, security, or implementation decision in this document is final.

Implementation note (2026-11-08): the local implementation uses Gmail's documented HTTPS token and `users.messages.send` endpoints through Node `fetch`, rather than importing the whole `googleapis` client. The full client import exceeded the local TypeScript memory limit. The separate operator OAuth client, `gmail.send` scope, and durability checks remain required. See the adjacent plan and runbook for implementation status and external prerequisites.

## Problem

Gastto has a public, static website that explains the product and links directly to its Telegram bot. The website has no email collection form, accounts, authentication, or calls to the token-consuming model API. Anyone who reaches the bot can currently begin onboarding. The team wants a controlled path for people whose Google account must first be added manually to the OAuth test-user list in Google Cloud, while ensuring that no model API call consumes tokens before the person completes Google OAuth.

The central coordination problem is that adding an email in Google Cloud does not update Gastto's own user or conversation state. Google documents managing test users in the Google Cloud console and enforcing eligibility during OAuth, but no documented public API for Gastto to list those test users has been identified. To notify a person *before* OAuth, Gastto needs a separate signal that the manual step is complete.

The reviewer's Google account email will already be listed as an allowed audience member in the Google Cloud console before the reviewer enters the bot. This does not associate the email with a Telegram chat in Gastto. The proposed chat flow applies equally to the reviewer and every other person. No website form is part of this proposal.

## Current behavior relevant to the proposal

- The first Telegram contact creates a local user, messaging identity, and `ONBOARDING_START` conversation state. See [`ResolveUserIdentity`](../../../src/application/use-cases/user/ResolveUserIdentity.ts).
- `/start` sends a welcome message. The onboarding worker currently asks the person to choose a storage provider, then sends the Google OAuth link after Google Drive is selected. See [`HandleStartCommand`](../../../src/application/use-cases/conversation/HandleStartCommand.ts), [`message.worker.ts`](../../../src/interfaces/workers/message.worker.ts), and [`InitiateCloudConnection`](../../../src/application/use-cases/spreadsheet/InitiateCloudConnection.ts).
- OAuth callback handling validates the flow state and stores encrypted tokens. OAuth reminders are scheduled after the link has been issued. See [`cloud-storage-connection.md`](../../../docs/features/cloud-storage-connection.md).
- Users and conversation states are stored in PostgreSQL; Redis is used for short-lived OAuth state and queues. The existing user status values do not represent an access request or manual approval. See [`data-model.md`](../../../docs/architecture/data-model.md).
- The OAuth request currently asks for Drive and Sheets scopes, not a Google account email claim. The email typed in Telegram therefore cannot currently be compared with a verified Google identity. See [`GoogleDriveOAuthAdapter`](../../../src/infrastructure/adapters/oauth/GoogleDriveOAuthAdapter.ts).
- `RegisterExpense.interpret()` checks for a usable OAuth access token before LLM extraction **when an active spreadsheet configuration exists**; without a configuration, that token check is skipped. The message worker can also invoke semantic routing before dispatching to the expense handler. Therefore, the existing check alone does not guarantee zero model calls before OAuth or after a credential failure across all paths. See [`RegisterExpense`](../../../src/application/use-cases/expense/RegisterExpense.ts), [`message.worker.ts`](../../../src/interfaces/workers/message.worker.ts), and [`RouteIncomingMessage`](../../../src/application/use-cases/conversation/RouteIncomingMessage.ts).

## Candidate flow

1. A person opens the bot and receives a fixed welcome message explaining the access process.
2. Gastto resolves the private Telegram `chat.id` to a local user. If the chat has an *approved* email association, the bot asks the person to write `continuar` to begin Google OAuth without asking for the email again.
3. If no approved email is associated with the chat, the bot asks for the Google account email intended for OAuth. It records the request as pending, tells the person that they will be notified when authorized, and sends an email notification to the operator about the new request. The same rule applies to the reviewer, even though their email may already be allowed in Google Cloud.
4. For a new request, an operator checks whether the email is already allowed in Google Cloud and adds it manually if needed. The operator then records approval in Gastto. Gastto associates the approved email with the chat and sends a Telegram notification asking the person to write `continuar`.
5. When the approved person writes `continuar`, Gastto generates and sends a fresh OAuth link. After a valid callback, Gastto marks access as completed and continues the existing spreadsheet onboarding flow.

This sequence remains a proposal rather than a complete implementation contract. The notification-and-`continuar` choice has been selected for the current proposal because the OAuth link can be generated when the person is ready to use it, avoiding an expired link in a delayed notification.

## Candidate persistence and approval mechanism

The selected storage is PostgreSQL. Each access request will be linked to Gastto's local `user_id`, which already resolves from the private Telegram `chat.id` through the existing messaging identity. The request will store the submitted email and at least `pending` or `approved` status. Candidate additional fields are creation and decision timestamps and an operator identifier. The CLI will approve pending requests; it will not offer a rejection action. Requests that are not approved remain pending unless replaced by a newer email from the same chat. A pending submitted email must not count as an approved association: otherwise, returning to the bot could bypass the waiting step. The exact table shape and indexes remain to be designed before implementation.

If a person submits a different email while their request is pending, the new email replaces the old one as the current email for that Telegram chat. The prior request must no longer be approvable, even if an older operator email is opened later. The operator notification must explicitly identify the Telegram chat and state that the new email replaces the previous email for that chat; it should include the previous and new email and an unambiguous current request ID. Keeping a superseded request in the database for audit is compatible with removing it as the chat's current email. If the old email had already been added to Google Cloud, the operator should remove it manually when no other person needs it. The replacement notice should make this cleanup visible, but it should not block the new pending request.

The bot will not offer a command to cancel a pending access request. Existing generic conversation-exit commands must not silently delete that durable request. A person can correct a pending email by submitting a replacement as described above.

Once a chat has an approved email, a different email can be requested only through the bot's `configuración` flow. The existing approved email and Google OAuth connection remain active while the replacement is pending and after the replacement email is approved. A failed, cancelled, or unfinished OAuth attempt leaves the old connection working. The operator email for this case must distinguish a pending change from an initial request and identify both the currently approved email and the proposed replacement.

After OAuth with the replacement account, the person must choose and validate a spreadsheet destination anew; Gastto cannot assume that account can access the previous file or sheet. The **old approved email, Google credential, and destination remain active until the replacement account completes OAuth and the newly selected spreadsheet is fully configured and confirmed**. A failure or cancellation anywhere in the new setup leaves the old setup active. The current settings OAuth callback validates a candidate against the *current* destination before replacing the credential, while the destination-change flow stages a file/sheet candidate separately. Combining account and destination change will therefore require additional design. The existing token schema permits only one token set per user and provider, so retaining both old and candidate credentials during this process would require a staged credential design and a coordinated final activation. See [`chat-spreadsheet-settings.md`](../../../docs/features/chat-spreadsheet-settings.md) and [`data-model.md`](../../../docs/architecture/data-model.md). Because the proposal does not compare Google identity emails, a successful callback does not prove that the newly approved email was the account used.

After the complete replacement setup is active, the operator should manually remove the former email from the Google Cloud test-user list **if it is no longer needed by anyone else**. This is a cleanup step after cutover, never a prerequisite for it. Removing a test user is not treated as proof that existing OAuth grants were revoked; any credential revocation or deletion needs separate design. Google's [OAuth best practices](https://developers.google.com/identity/protocols/oauth2/resources/best-practices) recommend revoking tokens that are no longer needed.

No Gastto approval-revocation feature is planned for this proposal. The operator can manage the Google Cloud test-user list manually if needed, but removing an email there does not update Gastto's local approval and must not be assumed to invalidate credentials already granted. Blocking an already authorized chat immediately would require a separate local access control and possibly OAuth token revocation; that is outside the current proposed scope.

For the current low-volume, manual approval process, the selected administrative action is a dedicated CLI command run inside the deployment. Only the project owner may execute it. It avoids adding an HTTP approval route to the public bot server. The command must approve a specific pending request, record the approval actor and timestamp, be idempotent, and trigger the applicant's Telegram notification after the approval is committed. It should use the application's approval use case rather than direct ad hoc SQL. The exact operator identifier used for auditing can be chosen during implementation; it must not be inferred from an untrusted CLI argument alone. A private endpoint could be considered later if approvals need automation; it would require its own strong authentication, function-level authorization, network exposure decision, rate limiting, and audit controls. See [OWASP API authorization guidance](https://api-security.owasp.org/editions/2019/en/0xa5-broken-function-level-authorization/).

Google Cloud remains the authority for its test-user list. For the proposed pending-and-notification flow, the operator must confirm that the email is allowed in Google Cloud, then mark the request approved in Gastto. The Gastto approval state should not be presented as proof that Google accepted the account. See [Google Cloud app audience](https://support.google.com/cloud/answer/15549945) and [OAuth app state overview](https://developers.google.com/identity/protocols/oauth2/production-readiness/overview).

## Model API admission rule to evaluate

The intended rule is that welcome messages, email collection, pending-status replies, approval notifications, and OAuth instructions use fixed application text and make no token-consuming model API calls. The rule covers every model provider, including semantic router shadow traffic. A central check should run before semantic routing or expense extraction and reject model work unless the user has completed the required OAuth flow **and has a usable Google credential**. If the credential stops working, model calls should be blocked again until reconnection. Model-calling use cases should also enforce the same condition, so a queued job or another entry point cannot bypass the worker check. The current `RegisterExpense` check is useful but insufficient for this rule because it is conditional on an existing spreadsheet configuration and runs after potential semantic routing.

The exact meaning of “OAuth completed” needs to be defined. A callback with a valid code and persisted token is the minimum candidate. This proposal will not require the Google account email to match the email submitted in Telegram. An expired access token that can be refreshed remains usable; a revoked or otherwise unusable credential closes model access until reconnection.

### Email-match decision and accepted limit

Google's test-user list, when the OAuth project is External and in Testing, blocks accounts outside that list during authorization. Therefore, comparing the Google account email with the one submitted in Telegram is **not required solely to block model calls before OAuth**. Without the comparison, however, an approved Telegram chat could authorize a *different* Google account that is also on the test-user list. The local approval and audit would then name one email while the linked Drive/Sheets credential belonged to another account. This matters if the approval is intended to authorize a specific person or Google account, rather than merely any account Google accepts.

For the current proposal, this mismatch risk is accepted and no email comparison is required. If the person selects a Google account outside the test-user list, Google rejects the authorization and the person can retry. If they select a *different account that is also allowed*, OAuth may succeed; Gastto would not detect the difference. Requiring a match later would mean requesting Google OpenID Connect `openid email` scopes and validating the identity during the callback. The current adapter requests only Drive and Sheets scopes. See [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect) and [OAuth app states](https://developers.google.com/identity/protocols/oauth2/production-readiness/overview).

## Reviewer access

The reviewer is a **product tester acting as a normal user**, not a GitHub code reviewer or a Google OAuth verification reviewer. They will use the **production Telegram bot and production Google OAuth project**. Their email will already be allowed in that Google Cloud project before they enter the bot. Under the common rule, the reviewer gives an email and waits for Gastto approval if their Telegram chat has no approved email association. The operator can then confirm the existing Google Cloud entry and approve the request in Gastto. If the chat already has an approved association, the bot asks them to write `continuar` to begin OAuth. The review setup needs the production OAuth callback and a safe test spreadsheet, plus a short walkthrough from `/start` through the flow. The relevant bot changes must already be deployed to production before a live product test. See [`deployment.md`](../../../docs/features/deployment.md) for the production app and branch mapping.

Two notifications have different recipients. A new pending request should trigger an **email to the operator** at a single administrator address configured through an environment variable in each deployment. Approval should trigger a **Telegram message to the applicant**, asking them to write `continuar`. Email to the applicant is not selected. The proposed mail provider is Gmail API, because the operator wants their personal `@gmail.com` address as the actual sender. The pending request must remain available even if its email notification fails.

### Proposed operator-email service

**Recommend Gmail API with the official `googleapis` Node.js/TypeScript client**, which Gastto already depends on, for these low-volume operator alerts. Google documents [sending through `users.messages.send`](https://developers.google.com/workspace/gmail/api/guides/sending); its [`gmail.send` scope](https://developers.google.com/workspace/gmail/api/auth/scopes) permits sending without mailbox read access, though Google classifies it as sensitive. The [official, widely used client](https://github.com/googleapis/google-api-nodejs-client) avoids an additional email SDK dependency. Repository popularity is a maintenance signal, not a security guarantee. This choice allows the authenticated personal Gmail account to be the actual sender.

Use a **separate OAuth client/project for the operator mailbox** rather than adding Gmail scopes to the product-user Google OAuth flow. Authorize only the operator's Gmail account; store its client credentials and refresh token as deployment secrets, never in source or request records. Give this connection only `gmail.send`; the product-user OAuth token must never be used for operator mail. For an External OAuth app in *Testing*, Google says [refresh tokens expire after seven days](https://developers.google.com/identity/protocols/oauth2/), so that status is unsuitable for reliable unattended notifications. Google [allows a personal-use exemption from verification](https://support.google.com/cloud/answer/13464323) for limited users, but publishing status, scope eligibility, any unverified-app warning, and actual token persistence must be verified for the separate project before implementation. An operator-mail authorization failure must be observable and recoverable without changing access-request status.

Keep the notification minimal: request ID, Telegram chat ID, submitted email, request type, and previous email where replacement applies. Persist the request before enqueueing delivery; retry transient failures and log permanent failures without losing or approving the request. Gmail API does not supply the same send-request idempotency key mechanism considered for Resend, so deduplication across worker retries needs a local delivery record and an explicit policy for ambiguous timeouts. A queue/outbox design and exact retry policy remain implementation choices. [Google discourages Gmail app passwords](https://support.google.com/accounts/answer/185833), so SMTP with an app password is not the proposed security-first path. [Resend](https://github.com/resend/resend-node) and [Postmark](https://postmarkapp.com/developer/user-guide/managing-your-account/managing-sender-signatures) remain alternatives only if a domain-controlled address can become the sender instead of the personal Gmail address.

Google documents limits for external OAuth apps in Testing status, including a test-user limit and seven-day test authorizations; these constraints should be checked against the actual production OAuth project configuration before relying on the review setup. See [Google Cloud app audience](https://support.google.com/cloud/answer/15549945) and [Google OAuth 2.0](https://developers.google.com/identity/protocols/oauth2).
