# Phase 2 deletion inventory and safety constraints

This is an implementation worksheet, not a description of shipped deletion behavior. The Phase 1 menu is disabled for destructive execution in production.

## PostgreSQL

`users.user_id` owns `messaging_identities`, `access_requests`, `conversation_states`, `expense_queue`, `oauth_tokens`, `candidate_oauth_tokens`, `spreadsheet_configs`, `expense_records`, and `operation_logs`. Configurations own column mappings, categories, subcategories, and payment methods. Candidate credentials also reference access requests. Delete `expense_records` before `spreadsheet_configs` because the expense-to-configuration foreign key has NO ACTION; deleting only the user row can fail or depend on FK timing. Include soft-deleted expenses and historical configurations. The existing `users.status` check permits only onboarding, active, and suspended; it cannot represent deletion progress without a migration.

## Concurrency and replay constraints

- The message worker, OAuth callback, OAuth reminder, and `/start` flow use the per-user Redis lock. The thin incoming worker and webhook enqueue path can still admit messages. A deletion barrier must be checked at ingress and again inside every worker or service before side effects; the DB must be authoritative if Redis is restarted. A cache miss that refills `identity:*` holds a PostgreSQL share lock until the Redis write completes, so the deletion transaction either waits for and then clears the cache key, or the lookup sees the barrier and does not refill it.
- Persist the barrier before attempting remote revocation. Any callback or refresh in progress at barrier time must settle or be fenced before credentials are removed; an external Sheets write that started earlier must settle before completion is reported.
- Existing identity resolution auto-creates missing accounts. After deletion, it can recreate a record from a late webhook or stale `/start`. Define an explicit fresh-registration handshake and bounded replay protection before activating deletion. A permanent personal tombstone is contrary to the requested data minimization.
- PostgreSQL and Redis cannot share one atomic transaction. The operation needs durable checkpoints and idempotent, user-scoped cleanup. Completion requires rechecking both systems and retained BullMQ payloads. A remote revocation failure cannot postpone local credential erasure.
- Hosted logs, backups, replicas, and exports require an operational deletion/restore policy. Do not claim these are erased by the application transaction.

## Outstanding proof before enabling deletion

1. Prove that an old worker whose Redis lease expires cannot write to PostgreSQL or Sheets after the deletion barrier opens. The existing worker invalidates conversation execution on lease renewal failure, but this is not a database fence for every write.
2. Verify every queue state and key family under concurrent job transitions, including a worker that was already executing when deletion began. The current PostgreSQL and Redis/BullMQ integration tests cover ordinary cleanup, active-job refusal, and identity admission ordering.
3. Verify hosted logs, backups, replicas, and exports and define restore quarantine before claiming all provider-held copies are removed.
4. Confirm the bounded `/start` replay window against Telegram delivery and deployment behavior; the 48-hour marker is a minimization trade-off, not protection against arbitrary replay years later.
