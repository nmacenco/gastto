### Phase 4: Harden ingress and configuration

**Public contracts:** The webhook secret accepts only 32–256 characters from `A-Z`, `a-z`, `0-9`, `_`, `-`; randomness is an operator generation requirement, not something a regex proves. Unauthorized requests return 403, or 429 once their limit is exceeded. Rate-limited callbacks return 429 before state lookup/consumption, token exchange, or messaging. Production `/documentation` routes return 404. Existing successful callback and webhook responses remain unchanged, subject to the validation distinctions in Phase 2.

- [x] Tighten `TELEGRAM_WEBHOOK_SECRET`; validate `ENCRYPTION_KEY` as exactly 64 hexadecimal characters before decoding. Update `.env.example`, all affected synthetic fixtures, startup tests, and config docs. Do not change persisted encryption format or rotate the AES key as part of this validation change. Test invalid lengths/characters and ensure config errors reveal field names, never values.
- [ ] Document operator-generated webhook secrets with at least 32 random bytes encoded in the accepted alphabet. For each environment, first rotate under the currently permissive application, then enforce the stricter schema. Coordinate automatic `setWebhook` in `registerWorkers.ts`: stop/drain old instances that could restore old registration, install the new secret, start consistent instances and verify registration/delivery. Record the brief retry window, retain pending updates (`drop_pending_updates` must not be enabled), and test canary delivery/replay safety. Do not promise zero downtime with the current single-secret contract. Roll back to a compatible application while retaining the new valid secret; never restore a compromised secret.
- [ ] Establish the Fly client-IP trust boundary using the actual deployment path and official header guidance. Test forged `X-Forwarded-For`, `Fly-Client-IP`, multiple hops, direct/internal requests, IPv4/IPv6 and shared NAT. Do not enable blanket `trustProxy: true`. Use proxy headers only when provenance is established; otherwise use the peer or a bounded shared fallback with the availability trade-off recorded.
- [x] Add a limiter backed by the existing Redis abstraction/connection lifecycle, with atomic increments and expiry, environment/route namespaces, bounded key cardinality and operation timeouts. Do not use supplied secrets, OAuth state/code, or arbitrary raw headers as keys. Configure and validate finite positive limits/window values; record concrete defaults and burst assumptions in an ADR before coding the limiter. Authenticate Telegram first and rate-limit only unauthorized attempts before parsing the body; place the callback limiter before handler effects. Authenticated Telegram bursts and `/health` bypass these buckets.
- [x] Define outage behavior: an unavailable limiter store still rejects unauthorized Telegram requests with 403; authenticated requests continue to their existing processing path and may fail if the queue is unavailable.
