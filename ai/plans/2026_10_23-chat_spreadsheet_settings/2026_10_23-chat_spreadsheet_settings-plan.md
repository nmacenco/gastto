# Plan: Chat settings for the connected spreadsheet

## Goal

Let users inspect their Google connection and spreadsheet destination, reauthorize Google, and change their spreadsheet or sheet from the chat. Keep the current destination active until a replacement is fully confirmed, and preserve the file associated with earlier expenses.

## Context

- Follow [AGENTS.md](../../../AGENTS.md), [plan conventions](../../../docs/plans/plan-conventions.md), [testing guidelines](../../../docs/testing/guidelines.md), [ADRs](../../../docs/adr/adr.md), and the existing [cloud connection](../../../docs/features/cloud-storage-connection.md), [file selection](../../../docs/features/select-spreadsheet-file.md), [sheet selection](../../../docs/features/select-sheet.md), [access validation](../../../docs/features/validate-spreadsheet-access.md), [column mapping](../../../docs/features/confirm-or-correct-column-mapping.md), [category confirmation](../../../docs/features/category-confirmation.md), and [undo](../../../docs/features/undo-last-expense.md) feature docs.
- The [message worker](../../../src/interfaces/workers/message.worker.ts) routes onboarding and expense states. Existing OAuth, file selection, sheet selection, mapping, and category flows provide reusable behavior.
- The [data model](../../../docs/architecture/data-model.md) and [spreadsheet configuration schema](../../../src/infrastructure/db/schema/index.ts) currently allow one configuration row per user. [Undo](../../../src/application/use-cases/expense/UndoLastExpense.ts) reads that row to locate an earlier expense. Replacing its file ID would risk deleting a row in the wrong file.
- The schema also enforces `chk_conversation_state`; each phase introducing persisted states needs a generated migration before its workers are deployed. The [configuration repository](../../../src/infrastructure/db/repositories/DrizzleSpreadsheetConfigRepository.ts) and [sheet confirmation](../../../src/application/use-cases/spreadsheet/HandleSheetSelection.ts) currently upsert on the full per-user unique index. Versioning must replace this write behavior as well as the lookup behavior.
- Review the [OAuth callback route](../../../src/interfaces/http/routes/oauth.callback.ts), [callback use case](../../../src/application/use-cases/spreadsheet/HandleOAuthCallback.ts), and [reminder](../../../src/application/use-cases/spreadsheet/SendOAuthReminder.ts): the route requires a code, the callback saves tokens before the final state transition, and reminders skip valid credentials and replace the flow payload. These need settings-specific handling.
- Follow [ADR-024](../../../docs/adr/ADR-024-guard-conversation-writes-and-financial-effects.md) and integrate with [session expiry](../../../src/application/use-cases/conversation/HandleExpiredSessions.ts). Keep financial execution claims protected, including unresolved claims in `IDLE`.

## Public contracts

- Add `SETTINGS_MENU`, `SETTINGS_OAUTH`, `SETTINGS_FILE`, `SETTINGS_SHEET`, `SETTINGS_MAPPING`, and `SETTINGS_CATEGORIES` to the persisted FSM in the phases that first use them. Settings payloads carry a unique flow ID and candidate destination, never OAuth credentials. Guard writes with the current persisted conversation revision, state, and expiry through `ConversationStatePrecondition`; do not treat a revision copied into a payload as authority. Keep settings commands deterministic and outside semantic expense routing.
- The chat command `configuración` opens a numbered menu with status, reauthorization, file change, and sheet change. `cancelar` clears an owned pending settings flow and returns to `IDLE`. During an active expense, ask the user to finish or cancel that expense first. Preserve the existing financial-claim guard before settings routing; an unresolved financial outcome cannot be cancelled or replaced by settings.
- Add `GetSpreadsheetSettings.execute({ userId }): Promise<SettingsSummary>`, where the summary contains stored credential status (`missing`, `revoked`, or `available`), provider, and nullable file and sheet names, but no token or account email. `available` means a non-revoked credential is stored, not that live access is verified; access-token expiry alone does not mean disconnected because refresh may succeed. Status inspection makes no provider calls and Spanish copy states that access has not been checked. Without a complete destination, show onboarding guidance instead of starting destination-dependent actions.
- Keep `ISpreadsheetConfigRepository.findByUserId(userId)` as the active-version lookup and add `findById(id)` for historical expenses. Add `SpreadsheetConfig.isActive` and a partial unique index enforcing at most one active configuration per user.
- Add `ActivateSpreadsheetConfiguration.execute({ userId, expected, candidate }): Promise<'activated' | 'stale'>`. The candidate contains its flow/proposal identity, source configuration ID, provider, file and sheet, `headerRowIndex`, confirmed column mappings and normalized headers, access-validation time, and reviewed category hierarchy. Discovery, mapping corrections, and category edits read and update this candidate only. Transient correction caches are scoped to the flow and proposal, never shared with another candidate or onboarding proposal.
- Activation checks the expected revision, unexpired settings state, absence of a financial claim, and unchanged source active configuration in one database transaction. It creates the new version initially inactive, persists its mappings and hierarchy, deactivates the former version, activates the replacement, and clears the FSM to `IDLE`. Any failure rolls back all local changes. Provider calls happen before the transaction; completion copy is sent only after commit. A stale operation makes no persistent changes and sends no success copy, including no cleanup of a newer flow.
- Settings expire after 30 minutes of inactivity. Accepted user interactions refresh this deadline through a guarded transition; reminders and background work do not extend it. Cancellation, expiry, and validation failure clear only the flow still owned by the expected revision. Clean up its correction cache, OAuth nonce, and reminder job as applicable after the guarded transition; never delete a successor flow's resources. Callback guards reject abandoned flows even if external cleanup fails.
- No new HTTP route or web UI is included, but the existing OAuth callback contract gains success (`code` and `state`) and denial (`error` and `state`) variants. `SETTINGS_OAUTH` retains the settings origin, flow ID, current destination identity, nonce, and original settings deadline through reminder rotations. Nonces retain the existing 15-minute TTL and reminders the 10-minute delay; reminders stop when the settings deadline expires.
- Google reauthorization validates read/write access to the current file and sheet using the newly exchanged credential in memory, without saving it first. Commit encrypted token replacement and the guarded transition to `IDLE` in one database transaction after rechecking ownership and destination identity. Denial, expiry, validation failure, and transaction failure preserve the prior token and configuration. Google account identity is not stored; access to the current destination is the enforceable check. Historical configurations preserve destination identity, but access to older files can still be lost; undo must report an access failure without falling back to the active file.
