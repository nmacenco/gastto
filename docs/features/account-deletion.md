# Feature: Account deletion request

## Purpose

Make the account deletion entry discoverable in Telegram settings and require an explicit, time-limited confirmation before any irreversible work.

## Behavior (development implementation)

- The settings menu displays `8. Eliminar cuenta` in development and production. The deletion action is disabled in production until complete erasure is implemented.
- The existing message worker checks the Telegram messaging identity against the internal user ID and acquires the per-user lock before handling the option.
- A development request records `screen: account_deletion` in the existing conversation state with a ten-minute expiry and explains the scope, irreversibility, and preservation of Google Sheets.
- Exact `ELIMINAR MI CUENTA` can start a durable deletion operation in development when the worker has the deletion repository and queue wired. The user receives an initiation notice; a separate worker resumes the operation and sends the completion notice. `cancelar` clears the pending state; expiry asks for a fresh request. Production still reports that deletion is unavailable.
- Confirmation is one PostgreSQL transaction: it verifies the bound messaging identity, the observed conversation revision, the exact pending screen, and database-time expiry; then it clears the pending state and inserts the deletion barrier. A repeated or stale confirmation cannot start another operation.
- `/eliminar_cuenta` is a recovery entry to the same confirmation flow when the ordinary settings menu is unreachable. It is routed before OAuth and access approval checks, but after identity matching and lock acquisition. Active incompatible flows receive an unavailable response.
- The development worker attempts Google refresh-token revocation, deletes local active and candidate tokens even if revocation fails, removes user-owned retained BullMQ jobs and Redis keys, then deletes PostgreSQL expenses before their configurations and account row. The account-erasure transaction locks the user row before deleting expenses, so a concurrent insert that references that user cannot enter between expense and account deletion. It never calls a spreadsheet deletion API.
- Active and candidate credential upserts, including settings credential commits, hold a shared lock on the account row and reject writes once the deletion barrier exists. Barrier creation takes the conflicting exclusive lock, so a write either finishes before the barrier or is rejected after it.
- Access request submission also checks the barrier under the account row lock; approval already uses the same lock and checks the barrier.
- Completion is sent on a best-effort basis. If Telegram cannot receive it, the account still remains deleted and the temporary operation identity is removed. A remote revocation failure produces separate instructions to remove Gastto from Google account connections.
- New message deduplication markers include a hash of the chat ID to isolate equal message IDs in different chats, plus a temporary owner index for targeted deletion. Legacy markers expire within 24 hours and contain neither a user ID nor a chat ID, so they cannot be attributed safely for individual deletion.
- The marker and its owner index are written in one Redis transaction. If Redis rejects either write, message routing fails so the incoming job can retry instead of leaving a marker without an owner index.
- Queue cleanup scans retained BullMQ states again after removing owned jobs. If an owned job remains or becomes active during the scan, the worker keeps the deletion barrier and retries instead of declaring completion.
- An account deletion row survives the user row until operational cleanup and notification complete. A recovery scan requeues pending operations. Ingress, message workers and OAuth access check the pending barrier. The webhook admits jobs only for existing identities and serializes queue insertion with barrier creation. Unknown Telegram chats are not processed until a new `/start`, which is an explicit re-registration path; an opaque 48-hour replay marker prevents immediate reuse of the same `/start` delivery.
- [Telegram's Bot API](https://core.telegram.org/bots/api) says updates are retained for at most 24 hours and recommends `update_id` for webhook replay detection. The 48-hour `/start` marker exceeds that provider retention window. A fresh `/start` has a new message ID and may register again after deletion; an old delivery within the provider window is rejected. This guarantee assumes Telegram delivery through the authenticated webhook, not a holder of the webhook secret replaying captured payloads after the marker expires.
- The development implementation has component and PostgreSQL/Redis integration tests. It is not yet activated in production because full cross-system race, hosted logging/backup, and restoration checks remain release gates.

## Production availability and privacy policy

The Telegram entry is still disabled when `NODE_ENV=production`. The sibling frontend's Spanish policy draft describes the request and confirmation, says production erasure is not enabled, and distinguishes active Gastto data from provider-held logs and backups. It must not be published as a claim of completed account deletion until the release gates below are satisfied. A person can contact Gastto through the policy's Telegram link to ask about their data; the current automated path must not be represented as available.

The [recovery runbook](../operations/account-deletion-recovery.md) records operator checks, remote Google removal guidance, restore quarantine, and the evidence missing for safe activation. A completed operation's temporary progress record is removed, so a backup from before deletion cannot currently be reconciled without an independent bounded erasure record. Production activation remains blocked by that gap, the Phase 2 stale-writer and active-job gates, and account-specific provider retention evidence.

The code also sends structured Pino events to stdout for the hosting platform and, when `SENTRY_DSN` is configured, unexpected HTTP errors to Sentry after a scrubbing hook. Events may contain account UUIDs or chat IDs. Search by those identifiers in each hosted system, where supported, to verify erasure. Local cleanup cannot remove hosted events, and their retention and per-account deletion capability remain unverified.

This inventory covers application-owned stores and external sinks visible in source. Hosted logs, backups, replicas, exports, and processor retention require Phase 3 operational evidence. The production action remains disabled until the listed races and retention limits are resolved.
