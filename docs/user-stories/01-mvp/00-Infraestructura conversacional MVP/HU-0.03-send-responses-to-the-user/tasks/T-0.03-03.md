### Task T-0.03-03: Implement retry with exponential backoff and 4xx handling

- **Description:** Enhance the Telegram sender adapter to automatically retry on server-side failures (HTTP 5xx) with exponential backoff delays of 1, 2, and 4 seconds (3 retries total). Client errors (400, 403) must not trigger retries; they should be treated as permanent failures and logged accordingly. Ensure that permanent failures do not throw uncaught exceptions that would affect other processes.

- **Architectural layer:** `Infrastructure`

- **Acceptance criteria:**
  - [x] On Telegram API 5xx response, the adapter retries exactly 3 times before giving up.
  - [x] Retry delays are 1s, 2s, and 4s (exponential backoff).
  - [x] On Telegram API 400 or 403 response, the adapter does not retry and immediately returns a permanent failure.
  - [x] After 3 failed retries, the adapter returns a failure result without throwing.
  - [x] All retry attempts and final outcomes are observable for logging purposes.

- **Technical dependencies (block the start):** T-0.03-02
- **Delivery dependencies (block the merge):** T-0.03-05

- **Estimation:** 1.5 hours

- **Suggested role:** Backend

- **Technical notes:** Implement retry either as a wrapper/decorator around the base HTTP sender or inside the adapter using a small internal helper. Use `setTimeout`/`sleep` for delays. Consider idempotency: Telegram `sendMessage` is not strictly idempotent, but for this MVP, duplicate sends on retry are acceptable. Log each attempt at the Infrastructure level; structured logging integration comes in T-0.03-05.
