### Task T-0.03-01: Define messaging output port interface

- **Description:** Create the application-level output port (interface) that defines the contract for sending messages to users. This port keeps the use cases agnostic of Telegram or any specific messaging provider. The interface should declare a method to send a text message to a given chat identifier and return a structured result indicating success or failure.

- **Architectural layer:** `Application`

- **Acceptance criteria:**
  - [x] An output port interface exists in the Application layer (e.g., `src/application/ports/output/messaging.port.ts`).
  - [x] The interface declares a method such as `sendMessage(chatId: string, text: string): Promise<SendResult>`.
  - [x] The return type discriminates between success and failure without exposing Telegram-specific errors to the Application layer.
  - [x] The interface is imported/referenced by no concrete infrastructure code yet (that happens in the next task).

- **Technical dependencies (block the start):** None
- **Delivery dependencies (block the merge):** T-0.03-02

- **Estimation:** 1 hour

- **Suggested role:** Backend

- **Technical notes:** Follow Clean Architecture boundaries: the Application layer owns the interface; the Infrastructure layer will provide the implementation. The use case (Application layer) contains all business logic and delegates messaging through this port. The route handler (Interfaces layer) only deserializes, validates, and delegates. An output port (Application layer) keeps the use case agnostic of the external service. This boundary must be established from this first task and enforced in code review for all subsequent HUs. Refer to `AGENTS.md` for the layer structure.
