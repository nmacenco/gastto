### Task T-0.02-06: Implement ordered processing guarantee

- **Description:** Ensure that multiple messages from the same user received in rapid succession are processed strictly in arrival order without loss. Integrate BullMQ (or synchronous in-order processing if queue setup is premature) so that each webhook request yields one job that is processed sequentially per user. The queue worker lives in `src/interfaces/workers/` and invokes the Application-layer router use case.

- **Architectural layer:** `Infrastructure`

- **Acceptance criteria:**
  - [ ] A BullMQ queue and worker are configured in `src/infrastructure/redis/` or `src/interfaces/workers/`.
  - [ ] Messages from the same `chat_id` are processed in FIFO order.
  - [ ] No messages are dropped under concurrent load (within reasonable limits).
  - [ ] The worker delegates to the Application router; it does not contain business logic.
  - [ ] Unit / integration test simulates 3 rapid messages and asserts order and individual responses.

- **Technical dependencies (block the start):** T-0.02-03
- **Delivery dependencies (block the merge):** T-0.02-07

- **Estimation:** 2 hours

- **Suggested role:** Backend / DevOps

- **Technical notes:** If BullMQ is not yet wired, this task may include the initial Redis queue configuration. Use `pnpm dev` to validate worker behavior. Keep the worker thin — it only deserializes the job and calls the use case, maintaining the Clean Architecture boundary.
