### Task T-0.02-03: Implement message router / dispatcher by type

- **Description:** Create an Application-layer use case that receives a `NormalizedPayload` and routes it to the correct downstream handler based on `MessageType`. The route handler (Interfaces layer) must **only** deserialize, validate, and delegate to this use case. **All** business logic — including the decision of which handler to invoke — lives in this Application use case. An output port (Application layer) keeps the use case agnostic of Telegram or any external service.

- **Architectural layer:** `Application`

- **Acceptance criteria:**
  - [x] Use case is defined in `src/application/use-cases/`.
  - [x] Routing logic covers: `TEXT` → text handler, `UNSUPPORTED` → unsupported handler, `MALFORMED` → malformed handler.
  - [x] The use case depends on an output port, not on concrete adapters.
  - [x] The Fastify route handler (Interfaces) does not contain business logic; it only calls the use case.
  - [x] Clean Architecture boundary is documented in code comments for code review enforcement.

- **Technical dependencies (block the start):** T-0.02-02
- **Delivery dependencies (block the merge):** T-0.02-04, T-0.02-06

- **Estimation:** 1.5 hours

- **Suggested role:** Backend

- **Technical notes:** This boundary must be established from the first task that touches business logic and enforced in code review for all subsequent HUs. Use dependency injection (or manual wiring in `src/config/`) to connect the output port to the concrete sender adapter.
