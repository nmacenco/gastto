### Task T-0.04-02: Implement state transition application use case

- **Description:** Create `TransitionConversationState` use case in `src/application/use-cases/conversation/`. It receives `userId`, `targetState`, `payload`, and optional `expiresAt`. It fetches the current state via the repository, validates the transition using the domain `canTransition()` guard, and delegates the atomic update to the repository. If the transition is invalid, it throws a domain error. The use case returns the new `ConversationState`. All business logic lives here; the worker/route must delegate to this use case.

- **Architectural layer:** `Application`

- **Acceptance criteria:**
  - [x] Use case accepts `userId`, `targetState`, `payload`, and `expiresAt`.
  - [x] It validates the transition with `canTransition(from, to)` before calling the repository.
  - [x] Invalid transitions raise a typed domain error (e.g., `InvalidStateTransitionError`).
  - [x] Successful transitions return the updated `ConversationState`.
  - [x] The route handler / worker only deserializes, validates, and delegates; no business logic in the Interfaces layer.

- **Technical dependencies (block the start):** T-0.04-01
- **Delivery dependencies (block the merge):** T-0.04-05

- **Estimation:** 2 hours

- **Suggested role:** Backend
