### Task T-0.01-05: Implement /start command use case and welcome message

- **Description:** Implement the application use case `HandleStartCommand` that processes incoming webhook messages and handles the `/start` command by returning a basic welcome message. The Fastify route handler must **only** deserialize the incoming payload, validate it, and delegate to this use case. **No business logic lives in the route handler.** This use case belongs strictly to the Application layer and exposes a clean boundary (input DTO + output DTO) that the Interfaces layer calls. Establishing this boundary now is critical: subsequent HUs will follow the same pattern, and collapsing it here would pollute the transport layer with business rules.

- **Architectural layer:** `Application`

- **Acceptance criteria:**
  - [x] `/start` command triggers the welcome message response.
  - [x] Use case is testable independently of the transport layer (Fastify).
  - [x] Response is sent back to the correct Telegram chat ID.

- **Technical dependencies (block the start):** T-0.01-02, T-0.01-03
- **Delivery dependencies (block the merge):** T-0.01-06

- **Estimation:** 1.5 hours

- **Suggested role:** Backend

- **Technical notes:**
  - Define a `HandleStartCommand` use case class in `src/application/use-cases/`.
  - Its input is a DTO (e.g., `{ chatId: string, username?: string }`), never the raw Telegram JSON.
  - Its output is a DTO (e.g., `{ replyText: string }`), never an HTTP response.
  - The Fastify route in `src/interfaces/http/routes/` maps the raw Telegram `Update` to the input DTO, awaits the use case, and maps the output DTO to the HTTP reply.
  - Define an output port (e.g., `IChatMessenger`) in `src/application/ports/` so the use case remains agnostic of Telegram.
  - The Telegram adapter in `src/infrastructure/adapters/telegram/` implements `IChatMessenger`.
  - This exact layering must be enforced in code review for all future HUs.
