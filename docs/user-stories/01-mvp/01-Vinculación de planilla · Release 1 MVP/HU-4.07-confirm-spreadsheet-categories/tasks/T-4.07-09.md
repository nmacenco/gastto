### Task T-4.07-09: Implement Telegram handler for category confirmation messages

- **Description:** Implement the Telegram route/handler that receives messages during the category confirmation flow. It deserializes and validates the incoming update, identifies the current conversation state, and delegates to the appropriate use case (detect/present, confirm, or add/correct). It formats the use-case response into Telegram messages and handles the final welcome message when onboarding completes.

- **Architectural layer:** `Interfaces`

- **Acceptance criteria:**
  - [x] Handler routes incoming messages based on the current conversation state.
  - [x] On first entry to the category step, it invokes the detect/present use case.
  - [x] On "yes"/equivalent, it invokes the confirm use case and sends the final welcome message.
  - [x] On add/remove/rename phrasing, it invokes the parser and then the edit use case, showing the updated list.
  - [x] Zod schema is declared for the route so Swagger auto-generates documentation.
  - [x] Errors are logged via Pino without leaking stack traces to the user.

- **Technical dependencies (block the start):** T-4.07-06, T-4.07-07, T-4.07-08
- **Delivery dependencies (block the merge):** T-4.07-10

- **Estimation:** 2 hours

- **Suggested role:** Backend

- **Technical notes:** This handler must respect the Clean Architecture boundary: it only deserializes, validates, and delegates. All business logic lives in the Application-layer use cases. Use `app.withTypeProvider<ZodTypeProvider>()` and declare `tags`, `description`, and `response` schemas per `AGENTS.md`.
