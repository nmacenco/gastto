### Task T-4.07-04: Implement detect-and-present categories use case

- **Description:** Build the Application-layer use case that orchestrates reading the spreadsheet category column (via the Infrastructure adapter), building or updating the user's `CategoryVocabulary` (Domain), and formatting a presentation message for the user. This use case is triggered after column mapping is confirmed (HU-4.06). If no categories are found, it must return the default set so the Interfaces layer can present it.

- **Architectural layer:** `Application`

- **Acceptance criteria:**
  - [ ] Use case accepts `userId` and `spreadsheetId` as input.
  - [ ] It calls the spreadsheet adapter to fetch unique category values.
  - [ ] It persists the resulting vocabulary via the repository port.
  - [ ] It returns a presentation DTO with the category list and a prompt message.
  - [ ] When no categories exist, the DTO contains the default category set.
  - [ ] Unit tests mock the adapter and repository, asserting the correct DTO output for both populated and empty columns.

- **Technical dependencies (block the start):** T-4.07-03
- **Delivery dependencies (block the merge):** T-4.07-05, T-4.07-06

- **Estimation:** 1.5 hours

- **Suggested role:** Backend

- **Technical notes:** The use case contains **all** business logic: deciding whether to build from spreadsheet values or defaults, normalizing names, and preparing the response. The route handler (Interfaces layer) **only** deserializes input, validates with Zod, and delegates to this use case. An output port (Application layer) keeps the use case agnostic of the Telegram or WhatsApp messaging service. Refer to existing use-case patterns under `src/application/use-cases/`.
