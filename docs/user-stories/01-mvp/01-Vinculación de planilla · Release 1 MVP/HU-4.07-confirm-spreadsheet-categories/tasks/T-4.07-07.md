### Task T-4.07-07: Implement Telegram conversation handlers for category confirmation

- **Description:** Add Telegram bot conversation handlers (Interfaces layer) that guide the user through category confirmation. The handlers must route messages to the correct use cases: detect-and-present (T-4.07-04), confirm (T-4.07-05), and add/correct (T-4.07-06). The handler deserializes and validates the incoming Telegram update, delegates to the Application layer, and formats the response message back to the user. This task also implements the empty-column default-set flow.

- **Architectural layer:** `Interfaces`

- **Acceptance criteria:**
  - [ ] Handler receives the category list from the detect use case and sends it to the user with the confirmation prompt.
  - [ ] Handler routes "yes" / affirmative replies to the confirm use case and sends the final welcome message.
  - [ ] Handler routes add/correct instructions to the modify use case and sends the updated list back.
  - [ ] When the spreadsheet column is empty, the handler presents the default category set and awaits user action.
  - [ ] Zod schema validates all route inputs for Swagger auto-documentation.
  - [ ] Fastify route tests register `validatorCompiler` and `serializerCompiler` from `fastify-type-provider-zod`.

- **Technical dependencies (block the start):** T-4.07-05, T-4.07-06
- **Delivery dependencies (block the merge):** T-4.07-08

- **Estimation:** 1.5 hours

- **Suggested role:** Backend

- **Technical notes:** The handler **only** deserializes, validates (Zod), and delegates. **All** business logic lives in the Application use cases. An output port in the Application layer keeps messaging agnostic of Telegram. Refer to existing Telegram route patterns under `src/interfaces/http/routes/`. Use the project's conversation-state manager (Redis/BullMQ workers) to track the user's current onboarding step.
