### Task T-4.07-07: Implement add or correct category use case

- **Description:** Implement the application use case that applies a parsed category edit (add, remove, or rename) to the current vocabulary. It loads the existing vocabulary, applies the change idempotently, persists the updated vocabulary, and returns the updated list for final confirmation. If the edit references an unknown category or produces duplicates, it returns a clear error with the current list.

- **Architectural layer:** `Application`

- **Acceptance criteria:**
  - [x] Use case accepts user/session identifier and a parsed edit command.
  - [x] Adding a category appends it if it does not already exist (case-insensitive).
  - [x] Removing a category deletes it if it exists; otherwise returns a not-found message.
  - [x] Renaming a category updates the name if the original exists and the new name is not a duplicate.
  - [x] After a successful edit, returns the updated list for reconfirmation.
  - [x] All business logic lives in the use case; ports keep it independent of storage and messaging.

- **Technical dependencies (block the start):** T-4.07-02, T-4.07-04, T-4.07-05
- **Delivery dependencies (block the merge):** T-4.07-09

- **Estimation:** 1 hour

- **Suggested role:** Backend

- **Technical notes:** The use case contains all business logic: deduplication rules, rename validation, and state update. The Telegram handler only deserializes the message and delegates to the parser + use case; storage details are hidden behind the vocabulary repository port.
