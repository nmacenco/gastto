### Task T-4.06-07: Implement Telegram handler for confirmation and correction messages

- **Description:** Add or update the Telegram route/handler that receives messages during the mapping confirmation flow. The handler deserializes and validates the incoming message, detects whether it is a confirmation ("yes/ok"), a correction ("no, the category is in column E"), an abandonment/resume signal, or a request to list available columns, and delegates to the corresponding application use case. It then renders the response back to the user.

- **Architectural layer:** `Interfaces`

- **Acceptance criteria:**
  - [ ] Route/handler is registered for the mapping confirmation conversation state.
  - [ ] It validates the payload with Zod and declares the schema for OpenAPI/Swagger if exposed via HTTP.
  - [ ] Confirmation messages delegate to the confirm use case.
  - [ ] Correction messages delegate to the correct field use case.
  - [ ] Invalid-column responses are rendered with the available column list.
  - [ ] Resume flow asks the user whether to continue from the saved state.

- **Technical dependencies (block the start):** T-4.06-03, T-4.06-05, T-4.06-06
- **Delivery dependencies (block the merge):** None

- **Estimation:** 2 hours

- **Suggested role:** Backend

- **Technical notes:** The handler must only deserialize, validate, and delegate. All business logic lives in the Application use cases. Use the output port pattern so the use case does not know it is being called from Telegram. Refer to existing `/webhook/telegram` route for Fastify + Zod patterns.
