### Task T-4.04-04: Implement validate spreadsheet access use case

- **Description:** Implement the Application-layer use case that orchestrates spreadsheet access validation. The use case receives the selected file/sheet identifiers, invokes the `ValidateSpreadsheetAccessPort` to read the preview and check write permissions, and applies business rules: (1) on success, return a transparent result to proceed to HU-4.05, (2) on read-only, produce a user-facing message explaining how to fix permissions, (3) on empty sheet, produce a message asking the user to confirm or choose another sheet, (4) on access error, retry once automatically, and if it persists, suggest reconnecting the account (back to HU-4.01). The use case must contain **all** business logic — no logic in the route handler. It must depend only on the domain port, not on concrete adapters.

- **Architectural layer:** `Application`

- **Acceptance criteria:**
  - [x] Use case is defined under `src/application/use-cases/` (spreadsheet subfolder).
  - [x] Depends only on the domain port `ValidateSpreadsheetAccessPort`, not on Google or Microsoft adapters.
  - [x] On success: returns a result that signals transparent progression (no user notification needed).
  - [x] On read-only: returns a structured result with user-facing message about missing write permission and how to fix it.
  - [x] On empty sheet: returns a structured result asking the user to confirm or choose another sheet.
  - [x] On access error: retries once automatically; if it persists, returns a result suggesting account reconnection.
  - [x] All four scenarios are covered by unit tests with mocked port.
  - [x] No business logic exists in the route handler (Interfaces layer).

- **Technical dependencies (block the start):** T-4.04-01
- **Delivery dependencies (block the merge):** T-4.04-05

- **Estimation:** 2.5 hours

- **Suggested role:** Backend

- **Technical notes:** Follow Clean Architecture boundary: the use case must remain agnostic of the external spreadsheet service. Refer to `AGENTS.md` architecture section and existing use cases under `src/application/use-cases/`. The retry policy should be configurable or at least clearly documented. Message strings should be centralized (i18n-ready if the project supports it).
