### Task T-4.04-05: Wire conversation handler to validate access

- **Description:** Wire the Interfaces-layer entry point (conversation handler or HTTP route) that triggers spreadsheet access validation. The handler must **only** deserialize the incoming request, validate input with Zod, and delegate to the `ValidateSpreadsheetAccess` use case. It must then map the use case's structured result to the appropriate user-facing response (or no response for the transparent success case). The handler must contain **zero** business logic. Register the adapter implementations in the dependency injection / composition root so the use case receives the correct port implementation based on the spreadsheet provider.

- **Architectural layer:** `Interfaces`

- **Acceptance criteria:**
  - [ ] Handler/route validates input with Zod schema and delegates to the use case.
  - [ ] No business logic (no permission checks, no retry, no message construction) in the handler.
  - [ ] On success: no message is sent to the user (transparent flow).
  - [ ] On read-only: user receives the "I can see your spreadsheet but I don't have permission to write to it" message with fix instructions.
  - [ ] On empty sheet: user receives the "sheet appears to be empty" message with confirmation prompt.
  - [ ] On persistent access error: user receives the suggestion to reconnect the account.
  - [ ] Adapters are registered in the composition root / DI container.
  - [ ] Integration tests verify the full flow from handler to mocked port.

- **Delivery dependencies (block the merge):** T-4.04-06

- **Estimation:** 2 hours

- **Suggested role:** Backend

Refer to `AGENTS.md` HTTP Routes & OpenAPI section — every route must declare a Zod schema. See existing routes (`/health`, `/webhook/telegram`) as reference. If this is a conversation step rather than an HTTP route, follow the existing conversation handler patterns in the project.
