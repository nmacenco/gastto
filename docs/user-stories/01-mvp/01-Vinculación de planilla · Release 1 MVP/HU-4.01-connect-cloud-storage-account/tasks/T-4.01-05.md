### Task T-4.01-05: Implement InitiateCloudConnection use case

- **Description:** Implement the Application use case that handles provider selection, generates the OAuth URL, stores the CSRF state in Redis, schedules the 10-minute reminder job, and sends the authorization link to the user via chat.

- **Architectural layer:** `Application`

- **Acceptance criteria:**
  - [ ] `InitiateCloudConnectionUseCase` created in `src/application/use-cases/spreadsheet/InitiateCloudConnection.ts`
  - [ ] Parses user input (raw message) to determine provider (`google` or `microsoft`) — accepts "1", "2", "Google Drive", "OneDrive" and variants
  - [ ] Invalid input returns a re-prompt message without changing state
  - [ ] Calls `OAuthServicePort.buildAuthUrl()` to generate the authorization link
  - [ ] Stores OAuth `state` in Redis with 15-minute TTL, mapping state → `{ userId, provider, externalId, channel }`
  - [ ] Schedules a BullMQ reminder job for +10 minutes on a new `oauth-reminder` queue
  - [ ] Sends the auth link via `MessagingOutputPort.sendMessage()`
  - [ ] Returns DTO with `nextState: 'ONBOARDING_DRIVE'`, `message`, and `payload`
  - [ ] Unit tests with mocked ports pass

- **Technical dependencies (block the start):** T-4.01-01, T-4.01-02
- **Delivery dependencies (block the merge):** T-4.01-09

- **Estimation:** 2 hours

- **Suggested role:** Backend

- **Technical notes:**
  - Clean Architecture boundary: this use case owns all business logic. The route handler (Interfaces) only deserializes, validates, and delegates. The `MessagingOutputPort` (Application output port) keeps the use case agnostic of Telegram/WhatsApp.
  - Use the existing `TransitionConversationState` use case pattern for state changes.
  - Redis key pattern: `oauth:state:{state}`.
