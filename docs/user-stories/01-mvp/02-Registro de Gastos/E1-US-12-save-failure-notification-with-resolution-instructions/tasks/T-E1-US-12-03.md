### Task T-E1-US-12-03: Preserve failed expense data with retry TTL

- **Description:** Extend the expense-saving Application flow so a failed save stores the complete confirmed expense payload in the persisted `EXPENSE_SAVING_RETRY` conversation state with a 10-minute expiration. Preserve the retry attempt metadata and ensure successful or terminal recovery clears the retry payload and returns the FSM to `IDLE`.

- **Architectural layer:** `Application`

- **Acceptance criteria:**
  - [ ] A failed save transitions the user from `EXPENSE_SAVING` to `EXPENSE_SAVING_RETRY` with the complete expense data required to repeat the append.
  - [ ] The retry state expires no earlier than 10 minutes after the failure and does not depend on Node.js process memory.
  - [ ] The original payload remains available when the user replies with the retry command.
  - [ ] Successful retry and terminal fallback clear the failed payload and leave the user in a valid FSM state.
  - [ ] Unit or repository-facing tests prove that the payload survives state reload and expiration metadata is set correctly.

- **Technical dependencies (block the start):** T-E1-US-12-01
- **Delivery dependencies (block the merge):** T-E1-US-12-04, T-E1-US-12-05, T-E1-US-12-06

- **Estimation:** 3 hours

- **Suggested role:** Backend

- **Technical notes:** Reuse `ConversationState`, `IConversationStateRepository`, and `EXPENSE_SAVING_RETRY` from ADR-003 and `docs/architecture/fsm-states.md`. Persist the payload through the existing PostgreSQL-backed FSM; “in memory” in the story means the data remains available for the retry window without being lost.
