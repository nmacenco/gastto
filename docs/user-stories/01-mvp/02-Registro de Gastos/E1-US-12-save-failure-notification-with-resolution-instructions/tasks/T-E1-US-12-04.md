### Task T-E1-US-12-04: Orchestrate failure notifications and recovery paths

- **Description:** Implement the Application use-case behavior for failed expense saves. Classify the typed failure, emit the corresponding centralized copy, preserve the retry payload for network failures, provide one-step reauthorization instructions for authentication failures, provide the canonical `reconfigurar` command for structure failures, and offer the manual-copy fallback after a retry failure. Ensure successful confirmation is called only after a confirmed append.

- **Architectural layer:** `Application`

- **Acceptance criteria:**
  - [x] Network failures send the connection message and the exact retry instruction `Responde 'reintentar' para intentarlo de nuevo.`.
  - [x] Authentication failures send the access message and one concrete reauthorization step without exposing technical details.
  - [x] Structure failures send the structure-change message and instruct the user to reply `reconfigurar` to start mapping reconfiguration.
  - [x] A successful retry invokes the existing E1-US-10 confirmation flow exactly once.
  - [x] A failed retry sends a clear terminal-failure message and a copyable representation of the expense data.
  - [x] No failure path invokes `expenseSavedConfirmation` or persists a successful expense record.

- **Technical dependencies (block the start):** T-E1-US-12-02, T-E1-US-12-03, E1-US-10
- **Delivery dependencies (block the merge):** T-E1-US-12-05, T-E1-US-12-06

- **Estimation:** 4 hours

- **Suggested role:** Backend

- **Technical notes:** Update the Application copy module and save orchestration around `RegisterExpenseUseCase` / `ResolveExpenseSummaryActionUseCase`. The external-trigger handler or worker only deserializes, validates, and delegates. The Application use case contains all business logic and uses output ports, remaining agnostic of Telegram, WhatsApp, and spreadsheet providers. Follow ADR-006 and ADR-012; log failures with structured fields through the injected Pino logger.
