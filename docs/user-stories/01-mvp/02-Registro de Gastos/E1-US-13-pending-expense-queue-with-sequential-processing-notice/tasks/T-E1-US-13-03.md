### Task T-E1-US-13-03: Orchestrate queue admission and advancement

- **Description:** Implement Application use cases that admit an incoming expense into the pending queue while an expense is active, enforce the 2-pending-item limit, and atomically advance the oldest queued message into the normal expense-processing flow after resolution. Add typed outcome/copy contracts for acknowledgement, full-queue rejection, pending-count notices, and final completion; do not duplicate LLM extraction or review logic.

- **Architectural layer:** `Application`

- **Acceptance criteria:**
  - [ ] Expense messages received during `EXPENSE_REVIEW`, `EXPENSE_CLARIFYING`, or `EXPENSE_CORRECTING` are queued without altering the active draft.
  - [ ] A third pending item is rejected with the specified full-queue copy and leaves no queue, state, audit, or expense-record trace.
  - [ ] Resolution advances exactly one oldest queued item, never starts two expense flows in parallel, and reports the current pending count after the preceding outcome.
  - [ ] When the final queued expense is confirmed, the closing copy includes the number of expenses registered in the sequence and returns the FSM to `IDLE`.
  - [ ] Unit tests cover admission, capacity release, FIFO advancement, no-queue resolution, and output-copy ordering.

- **Technical dependencies (block the start):** T-E1-US-13-01, T-E1-US-13-02
- **Delivery dependencies (block the merge):** T-E1-US-13-04, T-E1-US-13-05, T-E1-US-13-06, T-E1-US-13-07

- **Estimation:** 6 hours

- **Suggested role:** Backend

- **Technical notes:** All business rules belong in Application use cases, which depend on output ports (including `MessagingOutputPort`) and repository ports, never Telegram or WhatsApp adapters. Use the eager-advance rules in `docs/architecture/fsm-states.md`; persist the resolution before rendering messages.
