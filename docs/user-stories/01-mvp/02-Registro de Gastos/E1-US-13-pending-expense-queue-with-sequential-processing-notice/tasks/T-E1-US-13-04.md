### Task T-E1-US-13-04: Route rapid expense messages to the queue

- **Description:** Adapt the channel-agnostic incoming-message route and process-message worker integration so an expense-like message arriving during an active eligible expense state reaches the queue-admission use case and receives the normal immediate acknowledgement. Maintain per-user serialization and identical behavior for Telegram and WhatsApp adapters.

- **Architectural layer:** `Interfaces`

- **Acceptance criteria:**
  - [ ] Route/worker adapters only deserialize, validate, and delegate; they contain no queue capacity, ordering, or advancement business rules.
  - [ ] A second and third rapid expense are acknowledged in the existing immediate-acknowledgement path and queued in arrival order.
  - [ ] A rejected fourth expense returns the Application-layer full-queue outcome without interrupting the active review.
  - [ ] Existing duplicate-message and per-user locking guarantees remain in effect.
  - [ ] Adapter tests cover the delegation and preserve existing active-state routing behavior.

- **Technical dependencies (block the start):** T-E1-US-13-03
- **Delivery dependencies (block the merge):** T-E1-US-13-07

- **Estimation:** 4 hours

- **Suggested role:** Backend

- **Technical notes:** Follow `docs/features/incoming-message-routing.md` and ADR-005/ADR-011. The route handler only deserializes, validates, and delegates; the Application use case owns business logic through output ports, keeping it independent of external services.
