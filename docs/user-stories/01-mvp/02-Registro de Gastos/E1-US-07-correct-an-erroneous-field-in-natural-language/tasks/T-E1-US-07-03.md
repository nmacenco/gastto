### Task T-E1-US-07-03: Implement CorrectExpenseUseCase

- **Description:** Create `src/application/use-cases/expense/CorrectExpenseUseCase.ts`. This use case owns **all** the business logic of the correction flow. Inputs: `userId`, `rawMessage` (the user's correction), and the current `ExpenseReviewPayload`. Orchestration: (1) reconstruct the `ExpenseCorrectionState` from the stored payload; (2) call `llm.interpretCorrection` passing the current extracted expense as context; (3) if `interpretable === false` → return `'not_interpretable'` outcome (the worker sends the orientation message) and change nothing; (4) apply the changed fields to the current payload — amount/currency directly, category resolved through `ICategoryClassifier` so "transporte" maps to the user's spreadsheet vocabulary (reuses the E1-US-04 engine), and date resolved from `fechaRaw` with at least "ayer" → previous day, defaulting to today; (5) multiple field changes are applied atomically in one pass; (6) high-amount guard: if the corrected amount triggers the existing high-amount rule (`expenseRepo.findAverageAmountByUserId` × 10), set `pendingHighAmountConfirmation` so the presentation requests explicit confirmation before the change takes effect; (7) increment `correctionCycles`; if it exceeds the max (5), return `'cycle_limit'` offering confirm or cancel; (8) otherwise transition back to `EXPENSE_REVIEW` with the updated payload and a reset TTL, and return the updated payload so the worker presents a single updated summary.

- **Architectural layer:** `Application`

- **Acceptance criteria:**
  - [ ] Amount correction: "no, fueron 15" against amount=12 EUR updates the amount to 15 EUR
  - [ ] Category correction: "ponlo en transporte" resolves to the user's normalized category via `ICategoryClassifier`
  - [ ] Date correction: "fue ayer" resolves to the previous day
  - [ ] Multi-field correction: both fields are updated in a single execution and a single outcome is returned (never two presentations)
  - [ ] Unusually high corrected amount requests explicit confirmation (`pendingHighAmountConfirmation`) before applying
  - [ ] Uninterpretable message returns `'not_interpretable'` and modifies no data
  - [ ] Cycle counter increments; exceeding 5 returns `'cycle_limit'` and offers confirm/cancel
  - [ ] Successful correction transitions back to `EXPENSE_REVIEW` with the updated payload and resets the review TTL
  - [ ] The use case depends only on ports (`LLMPort`, `ICategoryClassifier`, repositories, `TransitionConversationState`) — no Telegram/WhatsApp or worker references
  - [ ] Unit tests cover every Gherkin scenario in the user story
