### Task T-E1-US-07-01: Define correction state value object

- **Description:** Create a typed `ExpenseCorrectionState` value object in `src/domain/value-objects/expense-correction-state.ts` that formalizes the payload shape of the `EXPENSE_CORRECTING` FSM state. Currently the FSM state exists (`FSM_TRANSITIONS` allows `EXPENSE_REVIEW → EXPENSE_CORRECTING` in `ConversationState.ts`) but `ResolveExpenseSummaryActionUseCase.handleCorrect()` stores the raw `ExpenseReviewPayload` cast to `Record<string, unknown>` without any typed contract. The value object must capture: the current `ExpenseReviewPayload` being corrected, a `correctionCycles` counter (max 5 per the Definition of Done), and an optional `pendingHighAmountConfirmation` flag for the explicit-confirmation path. This enables type-safe access across the Application and Interfaces layers.

- **Architectural layer:** `Domain`

- **Acceptance criteria:**
  - [x] `ExpenseCorrectionState` value object exists in `src/domain/value-objects/`
  - [x] It exposes typed fields: `payload: ExpenseReviewPayload`, `correctionCycles: number`, `pendingHighAmountConfirmation?: boolean`
  - [x] The maximum cycle count is a named constant set to 5 (DoD requirement)
  - [x] It is immutable and validated on construction (negative cycle count and payload shape are rejected)
  - [x] It is serializable to `Record<string, unknown>` for storage in `conversation_states.statePayload` and reconstructable from the serialized payload
  - [x] It exposes a method to produce the next state with an incremented cycle counter
  - [x] Unit tests verify construction, validation, serialization, and deserialization

- **Technical dependencies (block the start):** None
- **Delivery dependencies (block the merge):** T-E1-US-07-03

- **Estimation:** 1 hour

- **Suggested role:** Backend

- **Technical notes:** Follow the pattern of `src/domain/value-objects/expense-clarification-state.ts` (immutable, `toPayload()` / `fromPayload()`). `ExpenseReviewPayload` is defined in `src/application/use-cases/expense/RegisterExpense.ts` (fields: `extracted`, `rawMessage`, `resolvedDate`, `resolvedCategory`, `resolvedCategoryId`, `categoryStatus`, `awaitingZeroConfirmation?`, `reminderSent?`). The shape is already implicitly produced by `ResolveExpenseSummaryActionUseCase.handleCorrect()` — this task formalizes it into a named, validated type.
