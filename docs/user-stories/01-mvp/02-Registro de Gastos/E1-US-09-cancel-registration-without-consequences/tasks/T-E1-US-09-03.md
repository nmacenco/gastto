### Task T-E1-US-09-03: Integrate cancellation across expense-flow states

- **Description:** Add cancellation handling to the application conversation use case so that normalized cancellation inputs work during clarification, summary, correction, and any other active expense-registration state. The use case must clear the active context through the cleanup port, emit the correct confirmation through the output port, and reset the conversation so the next message starts a new registration.

- **Architectural layer:** `Application`

- **Acceptance criteria:**
  - [x] Cancellation is recognized in clarification, summary, correction, and other active expense-flow states.
  - [x] `no`, `cancel`, `cancel it`, `do not register`, `stop`, and `exit` cancel the active flow after normalization.
  - [x] Cancellation clears the active context before the confirmation is emitted and does not persist the in-progress expense.
  - [x] A cancellation request without an active flow produces a friendly no-pending-registration response without an error.
  - [x] A new expense message immediately after cancellation is processed with a fresh context and no data from the canceled flow.
  - [x] The route handler remains limited to deserialization, validation, and delegation; all cancellation business logic stays in the Application use case behind an external-service-agnostic output port.

- **Delivery dependencies (block the merge):** T-E1-US-09-04, T-E1-US-09-05

- **Estimation:** 3 hours
