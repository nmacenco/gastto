# Account deletion recovery and release quarantine

**Status:** Release procedure draft. Production account deletion remains disabled.

## What the current application can recover

`account_deletion_operations` is a temporary progress record. The recovery scan requeues a pending operation every minute. A failed Google revocation never preserves local ciphertext for an indefinite retry. The worker removes local credentials, account rows, owned Redis state, and retained queue jobs before a best-effort Telegram completion message. It removes the operation and its captured identities after that notification attempt. A failed notification does not restore data or retain the identity. The account's Google Sheets contents are outside this cleanup and must not be modified by it.

If Google revocation could not be confirmed, tell the person to open [Google Account third-party connections](https://myaccount.google.com/connections), choose Gastto, and remove its access. [Google's account help](https://support.google.com/accounts/answer/13533235) explains that removal prevents the app from accessing the account. Never request or log the person's Google token.

## Failure response before a restore

1. Keep the lifecycle-aware application running if its database and broker are healthy. Inspect only stage counts and structured error codes (`ACCOUNT_DELETION_JOB_FAILED`, `ACCOUNT_DELETION_RECOVERY_FAILED`, `ACCOUNT_JOB_STILL_ACTIVE`, `ACCOUNT_EXTERNAL_WORK_STILL_ACTIVE`). Do not print job payloads, tokens, messages, email addresses, or external chat IDs.
2. If PostgreSQL or Redis is unavailable, stop new ingress and worker processing. Repair the dependency, then allow the recovery scan to resume pending operations. Do not clear the barrier or treat an outage as successful deletion.
3. If an active job or registered external effect prevents cleanup, let it settle or fail under its normal lock. Retry deletion afterward. Do not remove its BullMQ lock or report completion while the job can still write.
4. For a remote revocation failure, verify local credential rows are absent and record only the bounded failure status already held by the temporary operation. Send the user the Google removal instructions. Do not retain refresh tokens for a later remote retry.
5. If final Telegram delivery fails, finish local cleanup and remove the temporary identity. The final message is best effort; do not infer delivery from a successful API call alone.

## Reconcile a stranded external-work count

Each external effect registers in `users.active_external_work_count` before it starts and decrements the count after it settles. Confirmation may create the deletion barrier while work is active; deletion must wait for the count to reach zero. A lost database connection or terminated process can leave a positive count, which deliberately blocks erasure. Do not use a timeout to clear it: a remote request may still finish after the database connection is lost.

1. Keep the account's deletion barrier in place. Stop ingress and workers that can act on that account, and verify that all processes from the affected deployment have exited. Prevent old instances from reconnecting during reconciliation.
2. Check the account-scoped count and pending operation stage without reading credentials or financial data. Reconcile outstanding provider calls and local writes, including Sheets operations, queue jobs, OAuth exchanges, and notifications. If an effect may still be running, keep the account quarantined and the count unchanged.
3. Once all prior processes are gone and each external effect is confirmed settled, verify the resulting account data and provider state against the deletion inventory. A controlled, audited operator repair may then set the stranded count to zero for that account only. Run the normal deletion recovery path and repeat the absence checks before reporting completion. Do not clear the deletion barrier manually.

This repair requires an account-specific incident record and operator review. There is no automatic counter reset or tested operator repair command yet, so a stranded count is a release rehearsal item.

## Quarantine a historical restore

The owner reported on 2026-11-21 that this Supabase Free project has never been paused or manually exported. On 2026-11-22 the owner identified Aiven as the production Redis provider and found three backups dated 2026-11-21 and 2026-11-22. The earlier report of no Redis backups is superseded. A strict no-historical-restore policy can still apply to PostgreSQL, but it cannot describe the existing Redis service. Aiven [restores the latest backup after a service power cycle](https://aiven.io/docs/platform/concepts/service_backups), which may recreate deleted account jobs, payloads, or cache keys if the backup predates deletion. Keep Fly ingress and workers disconnected from any restored Redis state until account-scoped cleanup is verified; a procedure alone cannot prevent a provider-initiated restart while the application remains connected. The release needs a tested detection/quarantine and cleanup design or an approved provider configuration that removes this restore path. Do not infer a one-day retention guarantee from the three visible backup timestamps. Provider-held logs and traces are separate retention concerns.

### Aiven Redis restore detection and remaining reconciliation work

1. Migrations `0021_dark_adam_destine` and `0022_glamorous_sprite` add a non-identifying, monotonically increasing cleanup epoch and a Valkey `run_id` in PostgreSQL. The app mirrors the epoch in Redis after verified account cleanup and before notification/completion. An interrupted write leaves the deletion operation pending. A snapshot from before cleanup has an older or missing mirror; a restarted Valkey server has a different `run_id`. This detector is implemented in development code and has focused integration coverage.
2. In non-production environments, the app checks both values before starting workers, on each HTTP request, and before each BullMQ processor can perform an effect. A mismatch or unavailable check returns HTTP 503 or fails a job with a fixed code. This is fail-closed for effects but may move unrelated jobs to failed during a prolonged incident; the current code does not pause all queue consumers or reconcile those jobs. CLI tools and other non-HTTP entry points still need an explicit recovery gate. The detector and deletion action remain disabled in production until recovery can be completed without losing unrelated work. Activation must enable both together.
3. In quarantine, run `pnpm redis:restore:inspect` from a trusted environment connected to the current PostgreSQL database and restored Redis. The command only reads; it reports counts, never IDs or payloads, and always says `safeToResume: false`. It scans retained BullMQ states, identity caches, correction state, OAuth nonces, and processed-message owner indexes. Jobs for current accounts are reported as uncertain because their outcome after the backup is unknown; orphaned jobs and keys are counted separately. The inventory does not yet establish complete Redis coverage or authorize cleanup. Remove only proven orphaned data in a future tested reconciliation flow; preserve unrelated live accounts. Do not replay any restored job whose outcome after the backup is unknown. A fresh `/start` receipt remains in PostgreSQL and must still be checked before reconnecting ingress. If ownership or job outcome cannot be established, keep the service quarantined and resolve it through an incident-specific process.
4. Reconcile the current Valkey `run_id` and epoch only after absence checks pass. No reset/reconciliation command exists. Rehearse a backup older than a completed deletion, a restore while Fly is still running, a connection loss between PostgreSQL epoch advance and Redis mirror write, and unrelated-account preservation. Count and error-code evidence only; no job payloads, identifiers, or credentials in logs.

The inventory's `jobDecisions` counts are advisory and grouped by queue. It validates each payload against the worker's schema and checks the current PostgreSQL owner and messaging identity. Use the following interpretation while the service is quarantined:

| Decision           | Meaning                                                                                        | Operator action before any reset                                                               |
| ------------------ | ---------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------- |
| `orphaned`         | The account or bound messaging identity is absent, or a deletion job has no pending operation. | Verify ownership and remove through a tested cleanup path; never replay.                       |
| `pendingDeletion`  | An account-deletion job still has a durable deletion operation.                                | Resume only after the restored Redis state is reconciled and the deletion barrier is verified. |
| `completedHistory` | BullMQ already marked the current-account job complete in the restored snapshot.               | Keep as history or remove under the normal retention rule; do not execute again.               |
| `failedHistory`    | BullMQ marked the job failed, but a partial external effect remains possible.                  | Check the effect outcome before deciding whether any retry is safe.                            |
| `unresolved`       | A current-account queued/active job or an ingress job without a bound user.                    | Determine the post-backup outcome using authoritative evidence; keep frozen meanwhile.         |
| `global`           | A schema-valid, empty session-timeout tick with no account payload.                            | Recreate only after ordinary scheduling and account-specific work are safe.                    |
| `invalidPayload`   | A job does not match the current worker schema or its queue is unknown.                        | Keep quarantined for manual inspection; do not print its payload in logs.                      |

An `active` count is reported separately; an active BullMQ lock must not be forcibly removed while a worker may still be running. No category is automatically replayable. A zero `unresolved` count alone is insufficient to reset the marker because key coverage, orphan removal, active work, and provider restore timing still need verification.

The epoch is a **restore detector**, not deletion of Aiven's provider-held backup. Those copies require a verified retention policy and accurate privacy disclosure. Disabling Valkey persistence is a separate operational option: [Aiven says `valkey_persistence=off` prevents future backups but loses all Redis data after a restart](https://aiven.io/docs/products/valkey/reference/advanced-params). It would discard BullMQ work and does not establish when existing backups expire. No production setting has been changed.

The following procedure applies to a PostgreSQL historical copy if one is discovered or introduced. It is **not** an authorization to restore that copy in production. Aiven Redis recovery must also remain quarantined until restored keys and jobs are reconciled against current PostgreSQL deletion state:

1. Keep every Fastify process, BullMQ worker, synchronous `/start` route, OAuth callback, and operator approval tool disconnected from the restored database. Do not point the production webhook or broker at it.
2. Restore into an isolated project or network. Do not switch the live `DATABASE_URL` to a historical snapshot. A backup taken before a completed deletion may contain the old identity, encrypted credentials, and expenses; it may lack the temporary deletion operation because that operation was later removed.
3. Reconcile every deletion completed after the backup's recovery point against an independent, bounded erasure record outside the restored database. For each matching historical `user_id`, delete all owned rows and operational state using the same verified deletion path. Compare aggregate counts of users, descendants, OAuth rows, Redis keys, and retained jobs before allowing traffic. Preserve all unrelated accounts. Do not print personal or financial values in the evidence report.
4. Test that stale webhook deliveries and `/start` messages cannot recreate a deleted identity, that active work has settled, and that no credential can be loaded. Only then reconnect the app, webhook, and workers.

**Historical-restore blocker:** No independent erasure record or tested reconciliation tool currently exists. The temporary operation row disappears after completion and cannot prove what a pre-deletion PostgreSQL backup must erase. A bounded keyed digest of the deleted user UUID and completion time in a separate failure domain is a candidate, with retention no longer than the longest verified restorable backup window. Its store, key custody, expiry, and re-registration behavior must be designed and tested before any historical PostgreSQL restore can be allowed. The existing Aiven Redis backups require their own tested fail-closed recovery path even if PostgreSQL historical restoration is prohibited. An old copy discovered later remains quarantined.

Before implementing that record, verify the longest period for which _any_ backup, PITR point, replica snapshot, or manual export can be restored. A finite record expiry is unsafe while an older copy remains restorable. The proposed record contains only a versioned keyed digest of the user UUID, completion time, and expiry; its HMAC key and storage must be outside the restored database. Writing it must be durable and idempotent **before** the temporary deletion operation is removed. A failed write must leave the operation pending and the production entry disabled. Key rotation must retain the ability to match every unexpired record.

An isolated restore rehearsal must supply a complete record covering the restored snapshot through quarantine time. Reject missing coverage, expired records needed by a restorable backup, unknown key versions, or digest mismatches. Match restored UUIDs inside the quarantined environment, remove only matched local account data and owned Redis/BullMQ state, and verify unrelated accounts remain. Do not use historical OAuth credentials or call Google, Telegram, or Sheets from the restored clone. Reconcile lost `/start` receipts or wait beyond the authenticated delivery window before reconnecting the webhook. Record only counts and pass/fail evidence; no raw identifiers, tokens, or financial values enter the report.

An object store outside Supabase is a candidate for the bounded record, pending owner selection and a verified backup window. [Cloudflare R2 lifecycle rules](https://developers.cloudflare.com/r2/buckets/object-lifecycles/) can expire objects after a configured period, but deletion is typically completed within 24 hours of expiry; [bucket locks](https://developers.cloudflare.com/r2/buckets/bucket-locks/) can extend retention. [Amazon S3 lifecycle rules](https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-expire-general-considerations.html) require separate handling of noncurrent versions when versioning is enabled. Verify the selected bucket's actual lifecycle, versioning, locks, copies, permissions, and key rotation before treating it as a bounded erasure record. No store has been selected or connected.

## Operator verification and release order

- Use parameterized, account-scoped count queries for `users`, `messaging_identities`, `access_requests`, `conversation_states`, `expense_queue`, `oauth_tokens`, `candidate_oauth_tokens`, `spreadsheet_configs`, `expense_records`, and `operation_logs`. Check configuration descendants by captured configuration/category IDs. Include soft-deleted expenses. Report counts only.
- Inspect Redis owner indexes, OAuth nonce ownership, correction state, and all retained BullMQ states for the account, including prioritized jobs. Do not use global key deletion or display payloads. Legacy unowned deduplication markers are subject to their 24-hour expiry, which must be included in any completion claim.
- Do not remove `account_start_replays` entries during per-account cleanup. They hold only HMAC digests and 48-hour expiry timestamps so a delayed `/start` cannot recreate an erased identity. The startup and hourly prune removes expired rows; check only the count of expired receipts if pruning fails. A database restore can lose newer receipts, so keep the webhook quarantined until replay protection is reconciled or Telegram's documented delivery window has passed.
- Apply migrations `0018_foamy_sersi`, `0019_tricky_leo`, `0020_bizarre_adam_destine`, `0021_dark_adam_destine`, and `0022_glamorous_sprite` before deploying workers or the webhook that query deletion state and the Redis restore marker. Record the applied migration names before deployment: CI has no migration step and the runtime image has no migration tooling. The operator must run and verify migrations from a separate trusted environment without exposing the database secret to the agent. Deploy lifecycle-aware ingress, workers, callbacks, and approval tools before enabling the production entry. The current `NODE_ENV=production` guard still disables the action; removing it is a separate release change.
- A rollback to code that ignores the barrier can resume processing accounts with pending deletions. Keep the lifecycle-aware version or keep all ingress and workers stopped until every pending operation is reconciled. Code rollback cannot undo completed erasure. Never restore an old database as a shortcut for rolling back deleted account data.
